# OOP Recap: The Four Pillars (and Interfaces)

> Patterns are built out of OOP mechanics. This is the vocabulary the rest of the course assumes.

## 🧠 Intuition

Object-oriented programming organizes code into **objects** — bundles of *data* (fields) and
*behavior* (methods) that model things in your problem domain. Four ideas hold it together:
**encapsulation, abstraction, inheritance, polymorphism**. Almost every design pattern is a clever
use of the last two — especially **polymorphism**.

> 💡 **Analogy — a car.** You *drive* it with a simple interface (pedals, wheel) without knowing
> the engine internals (**abstraction**). The internals are sealed under the hood (**encapsulation**).
> A SportsCar is a kind of Car (**inheritance**). And "press the accelerator" does the right thing
> whether it's an electric or petrol car (**polymorphism**).

## 📐 The Four Pillars

### 1. Encapsulation — bundle data + behavior, hide internals
Keep fields private; expose behavior through methods/properties. Outsiders can't put the object
into an invalid state.

```csharp
public class BankAccount {
    private decimal balance;                 // hidden — can't be set to garbage from outside
    public decimal Balance => balance;       // read-only view
    public void Deposit(decimal amount) {
        if (amount <= 0) throw new ArgumentException("must be positive");
        balance += amount;                   // the ONLY way balance changes
    }
}
```

### 2. Abstraction — expose *what*, hide *how*
Model the essential operations and hide the implementation behind an interface or abstract type.
Callers depend on the idea, not the details.

### 3. Inheritance — derive a class from another ("is-a")
`SportsCar : Car` reuses Car's members. Powerful but **easily overused** — see
[Composition & Principles](04.Composition-and-Principles.md) for why "favor composition" is the rule.

### 4. Polymorphism — one interface, many behaviors
The same call dispatches to different implementations at runtime. This is the **engine of nearly
every pattern** — Strategy, State, Observer, Decorator all rely on it.

```csharp
public abstract class Shape { public abstract double Area(); }
public class Circle : Shape { public double R; public override double Area() => Math.PI*R*R; }
public class Square : Shape { public double S; public override double Area() => S*S; }

Shape[] shapes = { new Circle{R=1}, new Square{S=2} };
foreach (var s in shapes) Console.WriteLine(s.Area());  // each runs its OWN Area()
```

## 🔑 Interface vs Abstract Class (a constant interview question)

Both let you program to an abstraction, but they differ:

| | Interface | Abstract class |
|--|-----------|----------------|
| Contains | A contract (and default members in modern C#) | Contract **+ shared implementation + state** |
| A class can have | **Many** interfaces | **One** base class |
| Relationship | "**can-do**" (capability) | "**is-a**" (identity) |
| Use when | Unrelated types share a capability (`IDisposable`, `IComparable`) | Related types share code/state |

```csharp
public interface IPayable { void Pay(decimal amount); }     // a capability anyone can implement

public abstract class Employee {                            // shared identity + code
    public string Name { get; init; }
    public abstract decimal CalculatePay();                 // subclasses must define
    public void PrintPayslip() => Console.WriteLine($"{Name}: {CalculatePay():C}"); // shared
}
```

**Rule of thumb:** default to an **interface** (it's more flexible — a type can implement many);
reach for an abstract class only when subclasses genuinely share code or state.

## ⚖️ Why This Matters for Patterns

- **Strategy / State / Observer / Command** all define an **interface** and swap implementations
  → polymorphism + abstraction.
- **Decorator / Proxy / Composite** all implement the **same interface** as the thing they wrap →
  abstraction.
- **Template Method** uses **inheritance** to share a skeleton.
- "Program to an interface, not an implementation" (the GoF motto) is just abstraction +
  polymorphism applied deliberately.

## 🚫 Common Mistakes

```csharp
// ❌ Leaky encapsulation: exposing a mutable internal list
public List<int> Items { get; } = new();   // callers can Items.Clear() behind your back
// ✅ expose a read-only view + intentful methods
private readonly List<int> items = new();
public IReadOnlyList<int> Items => items;
public void Add(int x) { /* validate */ items.Add(x); }

// ❌ Inheriting just to reuse code (a Stack IS-NOT-A List)
// ✅ compose: hold a List inside, expose only stack operations
```

## 🎯 Practice (with full solutions)

### 1. Choose interface or abstract class — `Easy`
**Task:** You have `Bird`, `Airplane`, and `Drone`. All can fly, but they share no code or
identity. How do you model "can fly"?
**Solution:** An **interface** `IFlyable { void Fly(); }`. They're unrelated types sharing only a
*capability* — exactly the interface use case (abstract class would force a false "is-a").
**Why it matters:** capability → interface; shared identity/code → abstract class.

### 2. Apply polymorphism — `Easy`
**Task:** Refactor this type-checking switch into polymorphism:
```csharp
double Area(object shape) {
    if (shape is Circle c) return Math.PI * c.R * c.R;
    if (shape is Square s) return s.S * s.S;
    throw new ArgumentException();
}
```
**Solution:** Give each shape its own `Area()` via a common base/interface (the `Shape` example
above), then just call `shape.Area()`. The `if/is` ladder vanishes.
**Why it matters:** replacing type-checks with polymorphism is the seed of many patterns (Strategy,
State, Visitor) and satisfies the [Open/Closed Principle](03.SOLID-Principles.md).

## ✅ Key Takeaways

- Four pillars: **encapsulation** (hide internals), **abstraction** (expose what, not how),
  **inheritance** (is-a), **polymorphism** (one call, many behaviors).
- **Polymorphism + abstraction** power almost every pattern.
- **Interface** = capability ("can-do"), many per class; **abstract class** = identity + shared
  code, one per class. Default to interfaces.
- Replace type-checking `if/switch` ladders with polymorphism.

**Self-check:**
1. Which pillar do Strategy, State, and Observer all rely on?
2. When do you pick an interface over an abstract class?
3. Why is exposing a mutable internal `List<T>` a violation of encapsulation?
