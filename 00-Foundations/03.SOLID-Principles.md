# SOLID Principles: The Five Rules Behind Good OOP Design

> The most important file in this module. Almost every design pattern exists to uphold one or more
> SOLID principles.

## 🧠 Intuition

SOLID is five principles (coined by Robert C. Martin) for writing OOP code that's easy to change,
test, and extend. You don't memorize them as trivia — you internalize them so that flexible design
becomes your default, and patterns become the *tools* you reach for to satisfy them.

> 💡 The unifying theme: **manage dependencies and isolate change.** Each principle is a different
> angle on "make sure a change in one place doesn't ripple through everything."

Each principle below: the one-liner, a ❌ violation, and the ✅ fix.

## 📐 The Five Principles

### S — Single Responsibility Principle (SRP)
**A class should have one reason to change** (do one job).

```csharp
// ❌ This class does three unrelated jobs — three reasons to change
class Report {
    public string Build() => "...";
    public void SaveToFile(string path) { /* file I/O */ }
    public void SendEmail(string to) { /* SMTP */ }
}
// ✅ Split responsibilities
class Report { public string Build() => "..."; }
class ReportFileSaver { public void Save(Report r, string path) { } }
class ReportEmailer { public void Send(Report r, string to) { } }
```
Now a change to email logic can't break report building.

### O — Open/Closed Principle (OCP)
**Open for extension, closed for modification** — add behavior without editing existing code.

```csharp
// ❌ Adding a shape means editing this method every time
double Area(object shape) {
    if (shape is Circle c) return Math.PI*c.R*c.R;
    if (shape is Square s) return s.S*s.S;
    // ...edit here for every new shape
}
// ✅ New shapes just implement the interface — existing code untouched
interface IShape { double Area(); }
class Circle : IShape { public double R; public double Area() => Math.PI*R*R; }
class Triangle : IShape { public double B, H; public double Area() => B*H/2; } // added, nothing edited
```
This is exactly what **Strategy**, **State**, and **Decorator** enable.

### L — Liskov Substitution Principle (LSP)
**Subtypes must be usable anywhere their base type is expected** — without surprises.

```csharp
// ❌ Square : Rectangle breaks callers that set width & height independently
class Rectangle { public virtual int Width, Height; }
class Square : Rectangle {                 // forcing W==H violates Rectangle's contract
    public override int Width  { set { base.Width = base.Height = value; } }
}
// A method expecting a Rectangle (set W=5, H=4, expect area 20) gets 16 → broken substitution.
// ✅ Don't force an "is-a" that breaks behavior; model them as separate IShape implementations.
```
Rule: a subclass must not **strengthen preconditions** or **weaken postconditions**.

### I — Interface Segregation Principle (ISP)
**Don't force clients to depend on methods they don't use** — prefer many small interfaces.

```csharp
// ❌ A fat interface forces a Robot to implement Eat()
interface IWorker { void Work(); void Eat(); }
class Robot : IWorker { public void Work() {} public void Eat() => throw new(); } // nonsense
// ✅ Segregate
interface IWorkable { void Work(); }
interface IFeedable { void Eat(); }
class Robot : IWorkable { public void Work() {} }       // implements only what it needs
class Human : IWorkable, IFeedable { public void Work(){} public void Eat(){} }
```

### D — Dependency Inversion Principle (DIP)
**Depend on abstractions, not concretions.** High-level code shouldn't depend on low-level details.

```csharp
// ❌ High-level OrderService is welded to a concrete SqlDatabase
class OrderService {
    private SqlDatabase db = new();             // hard to test, hard to swap
    public void Place(Order o) => db.Save(o);
}
// ✅ Depend on an interface; the concrete type is injected
interface IOrderRepository { void Save(Order o); }
class OrderService {
    private readonly IOrderRepository repo;
    public OrderService(IOrderRepository repo) => this.repo = repo;   // injected
    public void Place(Order o) => repo.Save(o);
}
```
DIP is the foundation of [Dependency Injection](../04-Modern-and-Enterprise/01.Dependency-Injection.md).

## 🔗 How SOLID Maps to Patterns

| Principle | Patterns that uphold it |
|-----------|-------------------------|
| SRP | Most patterns; e.g. Command (one request = one object) |
| OCP | Strategy, State, Decorator, Template Method, Visitor |
| LSP | Any polymorphic hierarchy; honest abstractions |
| ISP | Adapter, role interfaces; Interface-based designs |
| DIP | Dependency Injection, Abstract Factory, Repository |

## ⚖️ The Honest Caveat

SOLID is guidance, not law. Applied dogmatically it leads to a sprawl of tiny interfaces and
indirection ("over-engineering"). Use it to *reduce real pain*, not to chase purity — pair it with
[KISS/YAGNI](04.Composition-and-Principles.md).

## 🎯 Practice (with full solutions)

### 1. Spot the violation — `Easy`
**Task:** Which principle does this violate, and how do you fix it?
```csharp
class InvoicePrinter {
    public void Print(Invoice i) { /* format + send to printer + log to DB */ }
}
```
**Solution:** **SRP** — it formats, prints, *and* logs (three reasons to change). Split into
`InvoiceFormatter`, `Printer`, and a `Logger`, each with one job.
**Why it matters:** SRP keeps changes localized; it's the most commonly violated principle.

### 2. Refactor to OCP + DIP — `Medium`
**Task:** This needs editing every time a new payment method appears. Refactor it.
```csharp
class PaymentProcessor {
    public void Pay(string method, decimal amt) {
        if (method == "card") { /* card logic */ }
        else if (method == "paypal") { /* paypal logic */ }
    }
}
```
**Solution:** Introduce an abstraction and inject implementations (Strategy + DIP):
```csharp
interface IPaymentMethod { void Pay(decimal amount); }
class CardPayment : IPaymentMethod { public void Pay(decimal a) { /* card */ } }
class PayPalPayment : IPaymentMethod { public void Pay(decimal a) { /* paypal */ } }

class PaymentProcessor {
    public void Pay(IPaymentMethod method, decimal amt) => method.Pay(amt);
}
// New method? Add a class implementing IPaymentMethod — PaymentProcessor never changes.
```
**Why it matters:** this is **OCP** (closed to modification, open to new methods) achieved via
**DIP** (depend on `IPaymentMethod`) — and it's literally the [Strategy](../03-Behavioral/01.Strategy.md) pattern.

## ✅ Key Takeaways

- **S**RP: one job per class. **O**CP: extend without editing. **L**SP: subtypes substitute
  cleanly. **I**SP: small, focused interfaces. **D**IP: depend on abstractions.
- The common thread: **isolate change and depend on abstractions.**
- Most patterns are **tools to satisfy SOLID** — OCP especially (Strategy/State/Decorator).
- Apply it to reduce real pain; don't over-engineer in its name.

1. Which principle says "open for extension, closed for modification," and which patterns achieve it?
2. What does DIP invert, and how does it help testing?
3. Give an example of an LSP violation.
