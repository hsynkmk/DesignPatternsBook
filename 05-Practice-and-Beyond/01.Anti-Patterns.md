# Anti-Patterns: Common Traps and How to Escape Them

## 🧠 Intuition

An **anti-pattern** is a common "solution" that looks reasonable but causes more problems than it
solves. Knowing patterns is half the job; recognizing anti-patterns — including **misusing patterns
themselves** — is the other half. A senior developer is often defined more by what they *avoid* than
what they apply.

> 💡 The biggest anti-pattern of all is **"Pattern Fever"**: applying design patterns where simple
> code would do, in the belief that more patterns = better design. Patterns add indirection; only pay
> that cost when a real problem demands it ([KISS/YAGNI](../00-Foundations/04.Composition-and-Principles.md)).

Below: the anti-patterns you'll actually meet, why they hurt, and the way out.

## 📐 The Catalog

### 1. God Object (a.k.a. The Blob)
**What:** one class that does *everything* — thousands of lines, dozens of responsibilities.
**Why it hurts:** violates [SRP](../00-Foundations/03.SOLID-Principles.md); impossible to test,
understand, or change safely.
**Fix:** split by responsibility; extract collaborators; apply SRP. Often
[Facade](../02-Structural/02.Facade.md) + smaller services.

```csharp
// ❌ class OrderManager { /* validates, prices, charges, emails, logs, reports... 2000 lines */ }
// ✅ OrderValidator, PriceCalculator, PaymentService, EmailService — each one job
```

### 2. Singleton Abuse / Global State
**What:** using [Singleton](../01-Creational/05.Singleton.md) as a dumping ground for global mutable
state, or to avoid passing dependencies.
**Why it hurts:** hidden dependencies, untestable code, spooky action at a distance.
**Fix:** use [Dependency Injection](../04-Modern-and-Enterprise/01.Dependency-Injection.md) with a
singleton *lifetime* — one instance, but injected and mockable.

### 3. Anemic Domain Model
**What:** domain objects are just bags of getters/setters; *all* behavior lives in "service" classes.
**Why it hurts:** it's procedural code wearing an OOP costume; logic gets duplicated and rules aren't
enforced by the objects that own the data.
**Fix:** put behavior next to the data it operates on; let entities enforce their own invariants.

```csharp
// ❌ class Account { public decimal Balance { get; set; } }  // anyone can set any balance
//    class AccountService { void Withdraw(Account a, decimal amt){ a.Balance -= amt; } }
// ✅ class Account { public decimal Balance { get; private set; }
//        public void Withdraw(decimal amt){ if (amt > Balance) throw new(); Balance -= amt; } }
```

### 4. Service Locator
**What:** injecting the DI container and calling `container.Resolve<T>()` inside classes.
**Why it hurts:** hides what a class actually depends on (just like a global) — defeats the point of
DI and makes testing hard.
**Fix:** **constructor injection** — declare dependencies explicitly. (See
[DI](../04-Modern-and-Enterprise/01.Dependency-Injection.md).)

### 5. Big Ball of Mud / Spaghetti Code
**What:** no discernible architecture; everything depends on everything.
**Why it hurts:** every change risks breaking something unrelated; onboarding is brutal.
**Fix:** introduce layers/boundaries, dependency direction (DIP), and incremental refactoring toward
modules.

### 6. Golden Hammer
**What:** "When all you have is a hammer, everything looks like a nail" — forcing one favorite tool/
pattern onto every problem.
**Why it hurts:** wrong tool → awkward, fragile code.
**Fix:** match the tool to the problem; keep a broad toolkit (this course!) and consult the
[selection guide](02.Choosing-a-Pattern.md).

### 7. Premature Optimization
**What:** complicating code for performance before measuring whether it matters.
**Why it hurts:** harder code, often no real gain, sometimes *worse* (e.g. unnecessary caching bugs).
**Fix:** write clear code first; **profile**, then optimize the proven hotspots.

### 8. Copy-Paste Programming
**What:** duplicating code instead of abstracting it.
**Why it hurts:** bugs must be fixed in N places; behavior drifts apart.
**Fix:** [DRY](../00-Foundations/04.Composition-and-Principles.md) — extract shared logic (but don't
over-abstract things that merely *look* similar).

## ⚖️ The Nuance

Every "fix" above can itself be overdone. Splitting a class into 30 micro-classes is its own mess;
abstracting two coincidentally-similar lines couples unrelated code. The senior skill is **balance**:
remove real pain without manufacturing new complexity. Anti-patterns and over-engineering are two
ends of the same seesaw.

## 🎯 Practice (with full solutions)

### 1. Refactor a God Object — `Medium`
**Smelly code:** a `UserManager` that authenticates, hashes passwords, sends emails, logs, and writes
to the database — 1500 lines.
**Task:** identify the responsibilities and split them.
**Solution:** extract `IPasswordHasher`, `IEmailSender`, `IUserRepository`, and a thin `AuthService`
that orchestrates them (injected via DI). Each is single-responsibility and unit-testable.
```csharp
class AuthService {
    private readonly IUserRepository users;
    private readonly IPasswordHasher hasher;
    private readonly IEmailSender email;
    public AuthService(IUserRepository u, IPasswordHasher h, IEmailSender e) { users=u; hasher=h; email=e; }
    public void Register(string name, string pw) {
        users.Add(new User(name, hasher.Hash(pw)));
        email.Send(name, "welcome");
    }
}
```
**Why it's better:** SRP restored; each piece is mockable and reusable; the god object is gone.

### 2. Cure an Anemic Domain Model — `Medium`
**Smelly code:** `class CartService { void AddItem(Cart c, Item i){ c.Items.Add(i); c.Total += i.Price; } }`
with `Cart` exposing public mutable `Items` and `Total`.
**Task:** move the behavior into `Cart` and protect its invariants.
**Solution:**
```csharp
class Cart {
    private readonly List<Item> items = new();
    public IReadOnlyList<Item> Items => items;
    public decimal Total { get; private set; }
    public void AddItem(Item i) { items.Add(i); Total += i.Price; }   // rule lives with the data
}
```
**Why it's better:** the cart enforces its own consistency; `Total` can't drift out of sync; logic
isn't scattered in services.

### 3. Spot Pattern Fever — `Easy`
**Task:** A junior wraps a single, never-changing email-sending call behind an `IEmailStrategy`
interface, an `EmailStrategyFactory`, and a DI registration. Good or over-engineered?
**Solution:** over-engineered. With one implementation that never varies, the abstraction adds
indirection for zero benefit (YAGNI). A direct method call (or a simple injected `IEmailSender` if
testability is needed) is enough.
**Why it matters:** recognizing *unnecessary* patterns is as important as knowing them.

## ✅ Key Takeaways

- Anti-patterns are appealing "solutions" that backfire — learn to **smell** them.
- The worst is **Pattern Fever**: patterns without a problem add complexity, not quality.
- Classics: **God Object** (split it), **Singleton/global state** (use DI), **Anemic Model** (behavior
  with data), **Service Locator** (constructor injection), **premature optimization** (measure first).
- Every fix can be overdone — aim for **balance**, guided by [KISS/YAGNI](../00-Foundations/04.Composition-and-Principles.md).

1. Why is Service Locator considered an anti-pattern despite "using DI"?
2. What distinguishes an anemic domain model from a healthy one?
3. What's the cure for Pattern Fever?
